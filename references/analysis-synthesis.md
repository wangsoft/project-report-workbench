# 多视角分析、冲突综合与报告叙事

[English](analysis-synthesis.en.md) | 简体中文

在已确认的数据契约和指标表之上执行。目标是补足决策所需的分析覆盖、处理发现之间的关系，并组织可读报告；不能用专家角色名称代替方法依据。

## 1. 多视角问题清单

按决策问题和可用数据选择最少且互补的视角，不以行数或固定专家数量启动复杂流程。简单问题只用一个视角。默认在同一智能体中顺序执行；本规程不要求多 agent，也不新增角色审批环节。

| 视角 | 候选问题 | 必需证据/边界 |
|---|---|---|
| 增长与结构 | 总量变化来自哪些产品、渠道或客户？存量与新增是否分化？ | 可比期间、稳定分类与贡献计算；不能把构成变化直接称为原因 |
| 盈利与效率 | 收入变化是否转化为利润？成本、价格、销量和组合怎样变化？ | 成本与收入粒度一致；缺成本不能推断利润改善 |
| 客户与行为 | 留存、流失和购买频次是否变化？不同 cohort 是否分化？ | 客户级历史、窗口与分母明确；汇总表不能还原个体行为 |
| 运营与交付 | 产能、库存、履约或服务质量是否限制结果？ | 可用运营指标和时间对应关系；缺数据时列为待核查 |
| 风险与稳健性 | 集中度、缺失、极端值、口径变化会否改变结论？ | 原始分布、质量记录、敏感性或分组复算 |
| 统计与可比性 | 趋势是否受季节性、样本结构或不完整期间影响？ | 足够历史与适当方法；不为显得深入强行做预测/显著性检验 |

为每个选中问题记录 `question_id`、`lens`、决策用途、所需指标/方法 ID、证据是否可用和停止条件。缺证据的问题标为未回答，不补造答案；与决策无关的问题省略并简要记录原因。

先使用同一份冻结的指标表、数据截止日和契约分别检查各问题，再综合，不让第一条结论成为后续所有视角的预设。方法来源写真实引用，不扮演名人或暗示机构背书。

## 2. 结构化发现与冲突检查

沿用 [结论账本](contracts.md)，为需要综合的发现补充：主题、问题 ID、业务影响及其依据、支持/反证 claim ID、替代解释和推荐图表。重要性按决策影响、范围、紧迫性和证据强弱说明理由；不凭空计算综合得分或置信概率。

综合次序：

1. **对齐**：核对指标、期间、主体、币种、分母、过滤条件和版本。不同范围的发现不直接合并。
2. **去重**：相同事实保留一个 canonical claim ID，其余引用它；多个视角读同一数据不等于多份独立证据。
3. **分类**：区分重复发现、范围差异、算术矛盾、互补现象和竞争性解释。
4. **核查**：数字差异执行 [契约中的逐层核对](contracts.md)，定位第一个分歧点并记录残余；范围差异拆开表达；竞争解释寻找能区分它们的证据。解释依赖的实质假设使用 assumption ID 跟踪状态和影响，不只写在段落中。
5. **综合**：按业务主题组织，保留已确认的共同结论、尚未解决的分歧、所缺证据和对行动的影响。不能多数投票或取平均消除冲突。

关键数字矛盾未解决时，不发布受影响的确定性结论；其他不受影响的部分可继续。只有描述性共现时写“同时发生”，有分解证据时写“变化集中在”，具备因果识别或足够外部证据时才使用相应强度的因果表述。

### 综合示例（合成情境）

已知收入同比 +20%、利润 -10%、客户流失率上升：三者可同时成立，不能直接判为相互矛盾，也不能直接写成“低质量客户增长导致利润下降”。

- 先检查利润与收入是否同期间同范围，流失率是否采用相同客户定义。
- 若有成本/细分客户数据，分别核查成本增量和客户结构；记录支持与反证。
- 若没有，可写“收入增长尚未转化为利润改善，且客户留存承压”；将解释留为待核查，并列出所需成本、cohort 数据。

冲突记录保留 `conflict_id`、关联 claim ID、类型、核查动作、结果、未解决部分、受影响的结论/建议及最终处理状态。

## 3. 报告叙事组件

组件是内容契约，不强制 HTML、固定风格或固定章节数。使用项目 的 `visual-spec.md` 和页面模板呈现；同一套指标、结论 ID 和语义颜色服务 PDF/PPTX/文本输出。

| 组件 | 输入与结构 | 使用条件/不能做什么 |
|---|---|---|
| 执行摘要 | 决策问题 → 最重要的已核实结论 → 关键证据 → 决策含义/限制 | 按重要性挑选，不将所有章节复制一次；证据不足可直接说尚不能判断 |
| KPI 卡 | 指标、数值、单位、期间、比较基期、变化、状态与 claim ID | 缺基期不造变化率；箭头表示方向，颜色按指标好坏语义映射 |
| 发现与证据 | 结论式标题 → 数据/图表 → 解释边界 → 对决策的意义 | 标题的确定性不得强于正文证据；相关性不写成原因 |
| 对比/分解 | 比较对象和可比性 → 变化 → 贡献或结构 → 残余/未知部分 | 残余不得隐藏；没有分解数据不用归因版式暗示已经解释 |
| 风险与分歧 | 风险/冲突 → 支持与反证 → 影响范围 → 待核查事项 | 不用醒目风险卡夸大低证据猜测；未解决分歧不能只藏在附录 |
| 行动建议 | 动作 → 关联证据 → 前提 → 优先级理由 → 验证方式 | 区分立即行动、条件行动和补证据；责任人/期限/收益未给定时标建议或待定，不伪造承诺 |
| 来源与口径 | 文件/指标来源、截止日、单位、过滤、限制与账本定位 | 用户可读来源要足够定位；完整日志放运行目录，不堆满正文 |

通常采用“结论 → 证据 → 风险/限制 → 行动”的顺序，按读者与任务调整。每页突出一个主要问题，可用多个图表支持它；不要为了填满模板固定生成三条风险或五条建议。

标题示例：“销售额同比下降20%，降幅集中在华东”仅在两项结论均验证后使用；缺区域证据时只写前半句。无需因果证据的下一步可以是“核对华东缺货记录”，但不能写成“缺货导致下降”。

按主题整合而非按视角分章；保留必要的口径差异和解释分歧。若用户需要分析过程，将问题覆盖表与冲突处理记录放附录，正文不展示虚构专家署名。

## 4. 写入项目 与验收

将适用视角及问题触发规则写入 `analysis-rules.md`，将选用组件及内容绑定写入 `report-spec.md`，避免复制整份候选清单。问题覆盖、当期发现与冲突记录留在运行目录，不把单期事实固化为规则。

验收检查：重要问题有答案或明确缺口；重复证据未多次计权；未解决冲突可见且影响对应建议；摘要/标题/图表/正文使用同一结论；行动强度与证据相称。新增视角没有实质发现时允许不新增章节。
